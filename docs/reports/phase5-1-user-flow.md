## 2. 用户流程

### 2.1 主流程：从打开页面到看完证据链

```
打开 / ──→ ① 填生辰 ──→ ② 选主题 ──→ ③ 点「多主题分析」
   │                                      │
   │                                      ▼
   │                              POST /api/analyze/multi
   │                                      │
   │              ┌───────────────────────┼───────────────────────┐
   │              ▼                       ▼                       ▼
   │         【命盘区】              【证据链区】              【审查结论】
   │      四柱/藏干/十神/纳音        第一条命中的规则：          通过 / 未通过
   │      地支关系 / 缺五行          条件→出处→逐字原文         （含问题清单）
   │              │                       │
   │              │                       └── 典籍层规则带 URN 与可打开链接
   │              │
   │              └── 顶部一行：日主 · provider · 算法版本
   │
   └── 页脚常驻：确定性排盘（寿星天文历对拍）／规则可执行／典籍逐字回对
```

三个输出区默认 `hidden`，分析成功后才显示 —— **没有结果不出现空架子**。
任一主题失败时，证据链区顶部先列失败主题与原因，再渲染第一个成功主题；
全部失败时只显示错误，命盘区不显示。

### 2.2 两条旁路

| 旁路 | 入口 | 端点 | 输出区 |
|---|---|---|---|
| 只看命盘 | 「只看命盘」按钮 | `POST /api/chart` | 命盘区 |
| 流年时间轴 | 起止年 + 「流年时间轴」按钮 | `POST /api/timeline` | 时间轴区 |

旁路与主流程**共享同一份生辰输入**，不各存一份 —— 两处输入必然漂移，
这是信息架构里最常见的一种自伤。

### 2.3 错误流（当前实现的真实行为）

| 错误 | 来源 | 当前表现 | 5.2 起的目标表现 |
|---|---|---|---|
| 字段越界（月=13） | pydantic 请求模型 | 顶部一个错误框，一句中文串 | 同左，**加** `fields` 数组定位到具体输入框 |
| 日期不存在（2 月 30 日） | 引擎 `BirthInput` | 同上 | 同左（信息足够，不改） |
| 引擎边界年（第 1 年小寒前等） | 引擎 | 中文可读原因 | 不改 |
| 一个主题炸了 | 服务层故障隔离 | 证据链区顶部列失败原因 | 不改 |
| 全主题炸了 | 服务层 | 顶部错误框 | 不改 |

**设计决策：错误永远出现在顶部错误区，不弹窗、不 alert。**
页面是单栏阅读流，错误也是阅读流的一部分；弹窗会打断「填错→看红字→改」
这个最短修正回路。

## 3. 信息架构

### 3.1 页面分区与数据来源

| # | 分区 | DOM | 数据来源 | 显隐条件 |
|---|---|---|---|---|
| 0 | 标题与立场声明 | `h1` + `.thesis` | 静态 | 常驻 |
| 1 | 生辰输入 | `form` 第一行 | — | 常驻 |
| 2 | 主题选择 | `#topics` | 静态五项（事业/财运/婚姻/健康/命局） | 常驻 |
| 3 | 时间轴参数 | `form` 第二行 | — | 常驻 |
| 4 | 错误区 | `#error` | 任一请求失败 | 有错误才出现 |
| 5 | 命盘区 | `#out-chart` | `/api/chart`、`/api/analyze/multi` | 至少一个主题成功 |
| 6 | 证据链区 | `#out-analysis` | `/api/analyze/multi` | 至少一个主题有结果 |
| 7 | 时间轴区 | `#out-timeline` | `/api/timeline` | 时间轴请求成功 |
| 8 | 页脚 | `footer` | 静态 | 常驻 |

### 3.2 组件与字段路径（前端实际读取的响应路径）

命盘区读取：`day_master`、`provider`、`algorithm_version`、
`pillars[].{name,heavenly_stem,earthly_branch,hidden_stems,ten_god,na_yin}`、
`relations[].{type,branches,pillars}`、`elements.missing`。

证据链区读取：`topic_name`、`status`、`coverage_note`、`untraced_rules`、
`unreviewed_rules`、`strength`、`strength_breakdown.{supporting_rules,raw_support,saturation_k}`、
`chain[].{rule_id,conclusion,confidence,source_tier,review_status,is_production_ready,conditions,citation,urn}`、
`conditions[].{key,expected,actual,sources}`、`critique.{passed,issues}`。

时间轴区读取：`note`、`windows[].{liunian.{stem,branch},strength,dayun,report,signals}`。

这份清单是 **5.2 前端契约测试的基准**：静态提取 JS 里的字段路径，
对照真实 HTTP 响应逐条验证存在性 —— 路径漂移（后端改名、前端没跟上）
由测试抓住，不由用户抓住。

### 3.3 状态流转

```
idle ──提交──▶ pending ──成功──▶ shown（三区按条件显隐）
                 │
                 └──失败──▶ error（顶部错误区，输入保留）
```

输入**永不清空**：失败后用户改一个字段就能重试，清空输入等于惩罚出错的人。
时间戳、随机 ID 这类每次请求都变的值不进 UI —— 界面里没有任何东西
需要「刷新才准」。

## 5. 关键技术决策

### 5.1 不迁移框架，继续维护现有单页

任务书：优先维护现有前端，迁移需先交 RFC。**决策：不迁移。** 理由：

1. 现有页面零依赖、零构建，`python -m api.server` 起来就能用 —— 这与项目
   「新克隆可复现」的验收链（Phase 2 R4）是一体的。引入 React 意味着
   Node 工具链进 CI、进开发依赖、进新人上手路径。
2. 当前差距（G1–G16）全部是**组件级**差距，没有一条是「单页结构做不到」。
   为组件级差距换框架是用炮艇打蚊子。
3. 页面的核心资产是 `textContent` 渲染纪律（不用 `innerHTML` 拼用户可见
   数据）—— 这是安全属性，与框架无关，重写时弄丢的概率不小。

这条决策由本报告固定；谁想推翻，先写 RFC，别直接改。

### 5.2 错误信息的结构：detail 保留，fields 新增

422 响应**同时**给 `detail`（中文串，现有消费者与测试依赖它）与
`fields`（`[{field, message}]` 数组，前端逐字段渲染）。只加不改 ——
破坏响应形状是 API 层的重决策，不属于 5.2 的范围。

### 5.3 真太阳时是显式开关，不是自动行为

引擎默认民用时；真太阳时必须由用户勾选并提供经度。**不做「检测到经度
就自动校正」** —— 命理界对真太阳时的取用本身有分歧，自动切换会让
「这次排盘用的哪种时间」取决于用户填没填经纬度， quietly 改变结果。
显式开关 + 结果里看得见（算法版本号带 `+tst` 后缀），与项目
「计算口径必须可复现」一致。

## 7. 已知问题与风险

1. **主题层规则仍稀薄**（`destiny` 主题 13 条，其余主题层为空）——
   证据链在多数主题下只有公共结构层。这是知识层问题，不是产品层问题，
   Phase 5 不解决，只负责把它如实显示（`status=base_only` +
   `coverage_note` 已经在做）。
2. **重做丢的历史**：5.1 旧版内容不可考。若旧版做过本报告清单之外的
   审计发现，那些发现已丢失。缓解：差距清单是从 `081f6dc` 代码逐行
   重新审计得出的，不依赖旧版结论。
3. 时间轴跨 50 年上限（`MAX_TIMELINE_SPAN`）下前端一次渲染 50 个块，
   5.6 做交互时需要分页或虚拟化，否则 DOM 规模随跨度线性涨。
