# RFC：多流派策略与紫微斗数功能是否接入 V1.0

- **RFC 编号**：MingLi-RFC-0001
- **阶段**：Phase 3.8（命理可信核心收尾）
- **状态**：**有条件搁置（Deferred）**
- **提案对象**：多流派策略核（策略层基础设施）、紫微斗数子系统
- **相关提交**：`9b7d7a8`（Phase 3.7）、PR #1（已于 2026-10-18 按「拆两步」关闭）

---

## 1. 结论

**两项都不得接入 V1.0。**

| 提案 | 结论 | 一句话理由 |
|---|---|---|
| 多流派**策略核**（同一流派内的取用策略层） | 有条件搁置 | 它要解决的是「两法分歧时听谁的」，而这个系统现在的承诺是**如实报分歧**；策略核本质上是把裁决权收回来，会直接改掉一条已写进测试的核心行为 |
| 紫微斗数子系统 | 有条件搁置 | 没有排盘引擎，也没有可核验底本；`corpus` 里那块文本的 manifest 自述「尚無紫微斗數排盤引擎，故暫無規則原子可引用」 |

搁置不等于否定。§5、§6 给出各自的**准入条件**，条件全部满足时不需要新的 RFC 论证，按条件逐项验收即可。

---

## 2. 评审依据：本项目现有的、写下来的承诺

RFC 不能凭空表态，只能对着已经成立的约束表态。相关的四条：

1. **证据优先于解释。** 结论必须能追溯到命盘事实与典籍引文（Phase 3.2/3.5 已把这条链做成可解析、可端到端验证的）。
2. **分歧不自动裁决。** 同一结论槽上两条规则给出不同答案时，两条都留在证据链里，按冲突数扣减强度（`knowledge/rules.py: slot_conflicts`、`knowledge/evidence.py: score_strength`）。这条在 Phase 3.3 被明确写成测试：**「不静默丢弃任何一条分歧规则」**。
3. **不编造命理规则。** 典籍断语进入 ACTIVE 必须有可核验引文（单词条 + 底本 + 逐字原文 + URL + URN），由 `Rule.__post_init__` 构造期守卫，变异探针 M6 确认它被测试守着。
4. **不为了增加代码量引入框架。**（全局禁止事项）

任何提案先过这四条。

## 3. 多流派策略核

### 3.1 它是什么

PR #1 里的策略核，指的是「同一流派内部，多种取用方法之间的选择策略」——例如定格时本气定格与透干定格谁优先。它比「换一个流派」细一个层级，但改的还是同一个问题：**听谁的**。

### 3.2 为什么现在不能接入

**第一，名字撞了含义没撞。** master 的 `SchoolRegistry.schools` 是**命理流派**（structural_common / zi_ping_orthodox / di_tian_sui …），PR 的策略核是「同一流派内的取用策略」。同名不同义会让每一个 `school` 字段的语义同时含两个概念，而 `school` 是规则的一等字段、出现在证据链和 API 响应里。这不是命名洁癖：`test_the_two_tiers_partition_the_library` 这类测试按「流派」切分规则，语义一混，切分就不再完备。

**第二，它会改掉一条已经写进测试的行为。** 现在的同槽分歧是这样处理的：

```text
本气定格说正官格、透干定格说七杀格 → 两条都留着
→ conflict_notes 如实写「pattern_name 出现分歧：七杀格 / 正官格」
→ 强度按 CONFLICT_PENALTY × 1 扣减
```

策略核要做的是「按优先级挑一个」。挑完之后：分歧不见了，`conflict_notes` 恒空，强度不再被扣。**用户从「两种算法有分歧」变成「系统告诉我答案是七杀格」。** 这正是 Phase 3.3 测试里点名防的那件事，也是「不做预测」这条红线在规则层的落点。

注意：这**不意味着策略核永远不该做**。调候 vs 格局的优先级确实是子平法的真实问题。但它应该以「明确的学派主张 + 独立流派 + 有典籍依据」的形式出现，而不是以「悄悄地挑一个」的形式出现 —— 前者是可核验的立场，后者是不可见的取巧。

**第三，它只对两个流派有实际意义。** 当前有规则的流派只有 `structural_common` 与 `zi_ping_orthodox`，且典籍层只有 13 条、全部出自《三命通會》卷八的六甲日甲子时。在一层只有 13 条断语时引入取用策略层，是给一个还没有内容的系统先加一层调度。

### 3.3 接入条件（全部满足即可接入，无需再开 RFC）

| # | 条件 | 验收方式 |
|---|---|---|
| A | 命名统一：流派层与策略层在代码里是两个不同的概念，`Rule` 上有区分字段 | 静态测试：`school` 的取值域仅来自 `SchoolRegistry`；策略字段另有白名单 |
| B | 每个策略带来源：出自哪部典籍/哪一家成文体系，可核验 | 沿用典籍守卫：无来源的策略不许设为 ACTIVE |
| C | **分歧报出与策略裁决并存**：策略生效时，被裁决掉的那一方必须仍然出现在证据链里（如 `superseded_by`），`conflict_notes` 不能因此变空 | 测试：构造同槽分歧，断言两个结论都在、且策略选择有据可查 |
| D | 策略对强度的影响可复算 | `strength_breakdown` 多一项，且能被暴露字段互相算出 |
| E | 当前盘子够大，值得为它加一层 | 至少两个流派的断语各超过 30 条，且分属不同底本 |

A–D 是工程与契约条件，E 是规模条件。E 不满足时，即使 A–D 满足，接入也只是让系统更复杂。

## 4. 紫微斗数子系统

### 4.1 它是什么

新子系统：`engines/ziwei/` 排盘引擎 + 一批紫微规则 + `web/` UI。与现有八字引擎并列，最终让两种术数共用同一套证据链输出。

### 4.2 为什么现在不能接入

**第一，没有排盘引擎，规则无处落地。** 八字这边是「引擎 → 事实 → 规则 → 证据」四步，规则条件键落在 `FACT_SCHEMA` 里。紫微这边 `engines/` 下只有一个目录 `bazi/`。没有引擎，就没有命盘；没有命盘，规则条件无法计算，`RuleRegistry.match` 无从谈起。仓库自己的判断还留在 manifest 里：*「尚無紫微斗數排盤引擎，故暫無規則原子可引用 —— 先固化文本，引擎到位後再立原子。」*

**第二，底本未定。** `corpus` 里固化了《紫微斗數全書》卷一，但 role 是 `reserve`、edition 写着「維基文庫轉錄本（所據底本未標註）」。按 `Corpus.citation` 的门禁，`reserve` 不可供引用。这句话是关键：**现在绑上去的规则，一条都不能引用这段文本。**

**第三，它是 V1.0 之外的新子系统。** Phase 2 建立的质量门禁（四柱八字 + 证据链 + 评估）全部围绕一个引擎做。再引入第二个引擎意味着排盘精度验证、差分测试、边界扫描都要重做一遍。**这是范围问题，不是难度问题。**

**第四，PR #1 把三件事打成了一包。** +6352/−50、62 个文件，混着策略核、紫微引擎、Web UI。三者的评审标准不同（策略核改行为、紫微是新子系统、UI 是交互层），任何一者有疑义都拖累另两方。已在 PR #1 的关闭评论里给出「拆两步」方案。

### 4.3 接入条件

| # | 条件 | 验收方式 |
|---|---|---|
| F | 排盘引擎独立可测：有输入契约、有输出模型、有第三方案例或差分基准 | 引擎单测 + 一批可复算案例，`engines/ziwei/` 自己的 golden |
| G | 引擎与现有八字引擎隔离：`engines/ziwei/` 不 import `engines/bazi/` 的中间件，两者只共享最底层的定义表 | AST 扫描：反向着 0 条 |
| H | 证据链兼容：紫微事实进同一套 `Fact` 模型，来源文法（`resolve_source`）可解析 | `tests/test_fact_consistency.py` 扩到紫微命盘 |
| I | 底本转正：从 `reserve` 升为 `base`，即确认所据底本并逐条逐字核对 | 走 `fetch_corpus.py --fetch` + 现有引证守卫 |
| J | Web UI 是独立可接受的一步，不阻塞引擎 | UI 单独 PR，不依赖引擎 |

F–I 是硬条件，J 是顺序建议。**I 是最便宜也最容易被跳过的一条**，它只需要拿到一个可核验的底本，却决定了整个子系统能否接入「不编造」这条红线。

## 5. 如果以后要做：分步路线

按依赖排序，每步独立可评审、独立可回滚：

1. **统一命名**（无功能变更）—— 把流派与策略拆成两个概念，改字段与文档。这一步是为多流派铺路，也是 PR #1 的「第一步」。
2. **紫微排盘引擎**（新目录、零 import 八字）—— 做完只交付「能排出一张紫微命盘 + 自己的 golden」，不接 UI、不接规则。
3. **紫微底本转正** —— 与第 2 步并行，把 `reserve` 升 `base`。
4. **紫微规则层** —— 立原子、进证据链，复用现有四条引证守卫。
5. **多流派策略** —— 最后做，且必须满足 §3.3 的 A–D。此时流派已有真实规模，策略不会变成空中楼阁。

每一步都是一个 PR。第 1 步可以立刻做；第 2 步之后才是真正的投入。

---

## 6. 风险与回退

按本 RFC 的结论，**当前零代码变更**，因此没有回退动作。

若将来按 §5 推进，每条路线自带回退点：删掉新增的引擎目录与规则原子即可，八字侧的四个质量门禁与证据链不受影响 —— 这一点由 Phase 2 建立的模块边界保证（MingLi 与 CreatorOS 的隔离测试同理可扩到八字/紫微）。

---

## 7. 与 PR #1 的关系

PR #1 已在 2026-10-18 关闭并留下「拆两步」评论。本 RFC 是那次关闭的书面论证：**关掉它不是因为它做得不对，是因为它一次提出了三个不同性质的变更，而其中两个（策略核、紫微引擎）的准入条件当前不满足。**

评论里建议的第一步「先统一流派命名」，对应本 RFC §5 的第 1 步，随时可以做。
