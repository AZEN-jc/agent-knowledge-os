# 卷八六甲日十二时录入收口（Phase 6.12-6.13）

## 1. 修改了什么

卷八 60 节完成了前 12 节，即「六甲日」的全部十二个时辰。
累计 12 份原子文件、12 条章节登记、202 条典籍规则。本会话按 pstack 剧本

## 2. 为什么

老板四项决定中「内容深度优先」与「先吃透手头这一本」落在这个长跑项上。
六甲日十二时是一个天然边界：同一日干的十二时辰共享一套术语与断语结构，
录完它才能校准「一节要多少成本、词表够不够用」。

## 4. 数据结构

每条原子含 rule_id、URN、逐字引文、condition、转述断言、置信度、流派、
类别、校核状态。condition 只用 60 个既有事实键，第 3~12 节零新增键。

置信分布：MEDIUM 180 条，LOW 22 条。LOW 全部来自「原文自带限定语」或
「只录了合取条件的一半」，不是拍脑袋降权。

## 5. API

`/api/analyze/multi`、`/api/rules` 与报告导出。
端到端实测：真实分析 HTTP 200，命局主题 covered，新断语与人话条件都在链上。

## 8. 已知问题

**门禁耗时的根因已定位并修掉**，不是增量性问题，是重复构建。
`default_registry()` 单次 4.9 秒（重读语料 + 重放守卫），
`registry.match` 单次 1.6 毫秒 [实测 Measured]。
`matched_rule_ids` 对每张见证盘都重建一次注册表，202 张盘乘以三个测试函数
累积约 50 分钟。改成模块级 `lru_cache` 复用后，见证测试从 39m20s 降到 9.93s，
约 238 倍 [实测 Measured]。变异探针验证：撤掉缓存守卫测试立刻变红。

Phase 6.14 补记：`scripts/atom_checklist.py` 有同一个病，而且更严重 ——
重叠复核循环对 107 条登记各重建一次注册表，本机连续三次被 SIGTERM 杀掉。
已改为模块级复用并补守卫，从「跑不完」降到 5.9 秒。

剩余已知问题：其余测试文件各有自己的 `default_registry()` 调用，
全量测试仍会重复构建若干次（实测 29 分 06 秒）。这些文件里有
「新建注册表与基线同指纹」这类故意重建的断言，**不能全局套缓存**，
要逐个判断，否则守卫会变成永真。
