# MingLi Agent（命理智能体）

**可验证的命理推理系统 · Verifiable Chinese Astrology Reasoning System**

不是「会算命的聊天机器人」。排盘由确定性引擎算，结论必须能追到命盘要素与规则出处，
每一句典籍断语都要能在固化底本里逐字找到。

---

## 项目定位

- **确定性排盘** —— 排盘交给 `sxtwl`（寿星天文历），不让模型算命盘
- **规则引擎** —— 81 条规则：68 条结构层（由可执行定义表唯一确定）+ 13 条典籍层（带逐字引文）
- **证据链追踪** —— 每条结论的每个条件都能追到具体命盘要素，断环会被 Critic 拦下
- **可验证的引证体系** —— 典籍断语挂在固化底本上，改一个字就装配失败
- **流派透明** —— 分歧并列披露，不投票选一个「真答案」
- **不做预测** —— 信号是结构描述，强度是证据等级而非事件概率
- **持续评估** —— 30 案例 × 6 条行为不变量，可当回归门禁

## 核心架构

```text
                         用户 / API / Web UI
                                ↓
                        MingLiService（应用服务层）
                                ↓
        ┌───────────────────────┼───────────────────────┐
        ↓                       ↓                       ↓
   Bazi Engine             Knowledge                Time Engine
   engines/bazi            knowledge/               engines/bazi
   sxtwl 确定性排盘         规则库 + 引证体系          time_engine
        ↓                       ↓                       ↓
   四柱 / 藏干 / 十神      81 条规则 + 底本         流年 / 大运 / 流月
   纳音 / 地支关系         逐字引文 + URN                  ↓
        └───────────────────────┼───────────────────────┘
                                ↓
                    Evidence Layer  ★核心创新
              事实 → 条件追踪 → 证据链 → 强度算式
                                ↓
                      AnalystAgent（模板 或 provider 出稿）
                                ↓
                         CriticAgent（独立复核）
                                ↓
                    结论 + 证据强度 + 冲突 + 审查结果
```

**证据链的每一跳**：结论 → 规则 → 条件的期望值与实际值 → 命盘要素出处。
最后那一跳（`source`，如 `chart.pillars.month`）是「可追溯」落地的位置 ——
没有它，用户只能看到「规则要求正官」，看不到「正官来自月支藏干」。

## 核心创新一：证据层（Evidence Layer）

### 传统做法

```text
命盘 → LLM → 「你今年财运不错」
```

### MingLi Agent

```text
命盘
 ↓  确定性排盘（sxtwl）
四柱 己巳 丁丑 丁酉 丙午，日主丁
 ↓  事实提取（不带吉凶）
事实：日主有根 / 月支本气为食神 / 四支六害丑午 ...
 ↓  规则匹配（81 条，条件逐条追踪）
命中 13 条：STRUCT_ROOT_001、STRUCT_PATTERN_001 ...
 ↓  证据链（事实 + 规则 + 条件取值 + 命盘出处）
 ↓  强度算式（支持量凹饱和 − 冲突扣减）
结论（证据强度 0.79 —— 这是证据等级，不是事件概率）
```

用户能清楚看到：这个结论基于哪些规则？每条规则的哪个条件被什么命盘事实满足？
证据有多厚？不同流派怎么看？哪些依据还没校核过？

**强度为什么不用「置信度均值」**：均值完全不看命中条数 —— 命中 3 条和 20 条会得到
同一个分数。这里用 `raw / (raw + K)` 凹饱和：对条数单调递增、边际递减，
且**永远到不了 1.0** —— 结构层证据再厚也只是「命盘里有什么」，不该被读成「结论几乎确定」。

## 核心创新二：可验证的引证体系

典籍断语最大的风险不是写错，是**无从核对** —— 一句「《滴天髓》云……」可能是转抄的
二手话术。所以引文不是自由文本，而是一条能在固化底本里逐字定位的引用。

### 规范引用标识（Canonical Citation URN）

```text
urn:divination:bazi:sanmingtonghui:ws761697:j8.liujia_ri.jiachen_jiazi
     └─ 系统 ─┘ └书┘ └── 版本 ──┘ └卷.篇.条┘
```

`version` 段是刻意加的：同一部书有多个本子，共用 URN 会让反查回来的是错的元数据。

### 两级哈希

- `text_sha256` —— 我们归一化后的正文，用来发现**本地篡改**
- `source_revision_sha1` —— 上游 MediaWiki 的修订哈希，用来发现**上游漂移**

### 底本角色

| 角色 | 含义 | 可引用 |
|---|---|---|
| `base` | 底本，引文逐字回对的对象 | ✅ |
| `collation` | 同一部书的另一传本，用于核异文 | ❌ |
| `reserve` | 已固化、尚无消费方 | ❌ |

`Corpus.citation()` 拒绝任何非 `base` 的 URN —— 「两份都不可引、只有底本可引」的
门禁立得住，异文核对的结论才可信。

### 五条加载期守卫

一条原子写错不会抛异常，只会**静默地永远匹配不上**，或者更糟 —— 匹配上了但断错了。
所以装配期一次性挡住：

1. **逐字定位** —— `exact_quote` 必须在底本里逐字找得到（繁体转简体也算失败）
2. **键存在** —— 条件键必须在事实词表 `FACT_SCHEMA` 内
3. **元数据一致** —— 引用元数据与底本记录相符
4. **角色门禁** —— 非 `base` 不可引
5. **引文限制必须落进条件** —— 引文说了「申月」，条件里就必须有 `month_branch`

第五条来自一次真实事故：录甲辰日时「申月，煞星㑹印，俱貴」漏写了 `month_branch`，
引文逐字对得上、键都在词表、元数据也一致 —— 前四条一条都没拦，而 predicate
对**任何月份**都命中。前四条守的是「引文可核、键存在、元数据一致」，
没有一条问「引文说过的限制有没有落进条件」。

### 完整性自查

`Corpus.problems()` 校验两份正文的 sha256 与篇章表标签。哈希不符时**不再做派生检查** ——
拿一份「不知道被改成了什么」的文本去核篇名，报出来的「篇名找不到」只是哈希不符的副产品，
却会把诊断指向别的地方。

## 功能特性

### 排盘

四柱干支、藏干、十神、纳音、地支关系（六合/六冲/六害/相破/自刑/三刑）、五行计数。
年月柱按**节气精确时刻**分界（不是日期零点）；支持历史夏令时；晚子时口径显式可选。

### 规则库

81 条规则，每条带来源、流派、类别、主题、置信度、校核状态。

- **结构层 68 条** —— 十神有根/虚透、两种格局命名法、月令、日主强弱、五行缺失与偏旺、
  地支关系。由 `engines/bazi` 的定义表唯一确定，**跑一遍代码就能证伪**，不需要文献背书。
- **典籍层 13 条** —— 《三命通會》卷八「六甲日甲子時斷」，每条带 URN、逐字引文、
  底本与版本、可打开的出处地址。

**两种格局命名法并列收录**（本气定格 / 透干定格），它们只在月支本气不透而中气余气透干时
给出不同格局名 —— 那是真实分歧，系统并列输出，不投票。

### 流年与大运时间轴

- **流年** —— 干支对日主的十神、该十神在四支有没有根、流年支与命盘四支的结构关系（冲太岁等）
- **大运** —— 顺逆按阳年男/阴年女顺行；起运数到相邻的**节**（不是下一个立春）；
  三日折一年折算到日
- **流月** —— 由「节」划界，一个干支年恰好十二个月

输出形如 `2028年，信号：财星坐流年、六合巳、相破巳，证据强度0.44` ——
**不是**「2028 年你会发财」。区别不在措辞，在产出物本身：这一层没有任何一处
给出必然性判断，因为信号的定义就是「命盘里出现了什么结构」。

**大运需要性别**：顺逆规则不同流派有分歧，缺性别时只算流年、不猜默认方向。

### 多主题并发分析

`POST /api/analyze/multi` 一次分析多个主题，服务端并发执行。

- 命盘**只算一次**，扇出点在它之后，各主题共享同一张不可变命盘
- 主题之间无跨主题依赖，依赖图只有一层 —— 不需要 DAG 调度器
- **故障隔离**：单个主题失败不影响其余，失败项以 `ok=false` 如实带回原因
- 实测 4 主题 12 次 provider 调用：0.84s vs 串行估算 3.00s（**3.6x**）

诚实口径：确定性路径是纯 CPU 的，Python 的 GIL 让线程拿不到 CPU 并行度，
所以收益主要是故障隔离与故障定位；注入真 LLM 后每个主题是一次网络调用，
线程池这时才真正并行。

### 独立复核与审查

- **CriticAgent** 独立复算结论引用的规则是否都在证据链内，越界引用会披露
- **契约层** 只给模型证据链（不含原始命盘与全量规则库），只接受 `rule_ids` 与 `text` 两个键
- 契约本身可通过 `GET /api/llm/contract` 审计 —— 只写在源码注释里的契约等于没有契约

### Web 界面

`static/index.html` 单文件、无框架、无构建步骤。输入生辰 → 看命盘、证据链、
审查结果、流年时间轴。古典规则额外展示书名、底本、逐字原文与可点开的出处地址。

## 已知边界

- **年份支持范围是 2–9997**，且区间中部有 6 个失败年（899–901、999–1001）。
  这些年份上排盘会失败，返回 422 + 中文说明（`排盘失败：day is out of range
  for month`）。根因在 `engines/bazi` 的节气换算，属待修缺陷 —— 已在
  `tests/test_api_boundaries.py` 里钉住，修好引擎后那些测试会变绿。
- **大运需要性别**。顺逆规则不同流派有分歧，缺性别时只算流年、不猜默认方向。
  启用后结果带 `approximate: true`（三日折一年）。
- **LLM provider 未接线**。默认走确定性模板出稿，离线可运行；契约见
  `GET /api/llm/contract`。要接真 provider 就注入一个，接口只有
  `complete(request) -> str`。
- **典籍层只覆盖《三命通會》卷八「六甲日甲子時斷」**（13 条）。其余条目
  被阻塞在「拿到可核验底本」这一步，见 `GET /api/classics/backlog`。
- **紫微斗数排盘引擎未做**。`engines/` 下只有 `bazi/`；没有引擎，那批规则的
  条件无处落地。底本已固化挂 `role=reserve`，等引擎到位。
- **MingLi-Bench / fate-bench 未集成**。当前评估是自建的行为不变量检查，
  不是命理知识题准确率，因此**不给出准确率数字**。
- **主题层的断语覆盖不均**。事业/婚姻/健康/财运四个主题目前只有公共结构层证据
  （`status=base_only`），结论不构成对该主题的判断，`coverage_note` 里写了原因。

### 输入上限（公开契约）

接口对输入的约束是公开契约的一部分，OpenAPI 的 `description` 里都写了：

| 参数 | 上限 | 超限行为 |
|---|---|---|
| `year` / `start_year` / `end_year` | 2–9997 | 422 + 中文说明 |
| `question` | 200 字 | 422 |
| 主题名 | 20 字 | 422 |
| `topics` 条数 | 8，且不得重复 | 422 |
| 时间轴跨度 | 起止最多相差 50 年 | 422，提示分段查询 |

**错误消息一律是可直接展示给用户的中文。** 这是 `api/server.py` 模块 docstring
写下的契约，由 `on_validation_error` 保证；`tests/test_api_boundaries.py`
把「每个越界输入的 `detail` 都是中文」钉成了一条测试 —— 删掉那个处理器它会立刻红。

## 最近的变更

### 时间轴引擎（Phase 6 收口）

- 新增 `knowledge/flow_facts.py`：流年/大运对日主的十神、有根判定、与四支的结构关系。
  两条轴共用一份实现，只靠轴名前缀区分。
- 新增 `knowledge/time_windows.py`：`TimeWindow` / `Signal` / `analyze_period`。
  信号由事实直接命名并带 `source` 可回溯；主题过滤用显式声明的表。
- 强度公式内核提为 `score_support`，本命局与时间轴**共用同一算式** ——
  「本命局 0.62，2028 年 0.48」要有意义，两边必须是同一种东西。
- 接入 `POST /api/timeline`，Phase 6 的代码从死代码变成可用端点。

### 多主题并发

- `MingLiService.analyze_multi()`：命盘只算一次，扇出点在它之后；
  `analyze` 拆出「吃已算好命盘」的内核，两条路径共用，不另写一份。
- 标准库 `ThreadPoolExecutor`，不建队列、不建消息总线 —— 进程内传不可变 dataclass 就够。
- 故障隔离 + `POST /api/analyze/multi`。

### 引证体系与典籍层首批规则

- 固化公版底本（《三命通會》卷八，欽定四庫全書本），两级哈希 + 永久链接。
- `knowledge/urn.py`：Canonical Citation URN。
- 五条加载期守卫（含新增的第五条「引文说过的限制必须落进条件」）。
- 甲辰日甲子时七条断语解除暂缓，规则 68 → **81**，`destiny` 主题 6 → 13 条。
- `Corpus.problems()` 完整性自查补厚到各 5 条测试。

### Web 界面

- `static/index.html` 单文件，无框架无构建；`python -m api.server` 即起。
- 全程 `textContent` 不用 `innerHTML` —— 结论、规则原文、书名来自语料，
  生辰来自用户输入，拼 HTML 字符串等于自己开一个注入口。

### 评估门禁

- `evaluation/runner.py`：10 金标准案例 × 3 主题 × 6 条行为不变量。
- 评估器自身可被证伪：每条不变量都喂一份故意违规的 payload 断言报错。

### 测试与工具

- `scripts/atom_checklist.py`：新增原子的收口清单，四处同步从靠人记得变成可查。
- 见证命盘独占性检查：一张见证盘只该命中它见证的那条规则，多命中的要显式登记。

| `pytest` | 测试 |
| `rich` | 终端输出 |
| `requests` / `python-dotenv` | 语料抓取与配置 |

### 其余

- **前端** —— 原生 HTML + CSS + JS 单文件，无框架、无构建步骤
- **存储** —— 语料用 JSON + 纯文本固化在仓库内（`corpus/canonical/`）；
  运行日志用 JSONL。**没有数据库**：规则库是代码，语料是固化文件，
  两者都不需要运行时存储

### 为什么没有 PostgreSQL / Redis / React / LangChain

规划早期列过这些，实际做下来不需要：规则库与语料都是**版本化的静态资产**
（要的是可 diff、可复核，不是可查询），界面只需一个页面（引入构建步骤
就多一类构建故障），而模型调用被刻意收窄成一个 `complete(request) -> str`
—— 接口越窄，能绕过证据链的地方就越少。

## 设计原则

1. **计算与推理分离** —— 模型不负责计算，只负责理解问题与解释证据
2. **证据前置** —— 先有事实和规则，再有结论
3. **可验证高于可读** —— 引文必须逐字可回溯，宁可留白也不写「大概是这样」
4. **流派透明** —— 不同流派的判断差异必须明确告知用户
5. **不做预测** —— 输出结构信号与证据等级，不输出必然性判断
6. **本地优先** —— 核心计算可离线运行，不依赖外部服务
7. **接口越窄越安全** —— 能绕过证据链的地方越少越好
8. **诚实留白** —— 没有可核验底本时拒绝录入，并说明卡在哪一步
